# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

"Canvas & Co.": a store for paintings and handmade art (clay art and toys, crochet art, handmade decor). Next.js 16 (App Router, TS strict) + Tailwind 4 + Drizzle on Postgres + Better Auth (email/password) + Razorpay (**test mode only**, INR). It lives inside `book-now/` but is a separate project with its own `package.json`/`node_modules`, git repo and database; it was cloned from the sibling `ecommerceapp` (Thread & Co., a clothing store) and the core money/stock/ops code is identical, so fixes usually need applying to both. Not yet pushed or deployed: no remote, no hosted DB/Redis/Resend/Axiom/Sentry accounts exist for it. Only commit/push when asked.

**Catalogue model:** paintings have three size variants (Small/Medium/Large) whose names, **dimensions** and prices are admin-editable; other categories are single "One size" variants (dimensions text like "12 cm tall"). Variant `options` = `{ Color: "Default", Size, Dimensions? }` and `label` = `"Size · dimensions"` (the label becomes part of the order line name, so it avoids parentheses). The colour axis still exists in `AddToCart` but is hidden when there is one colour. Images are generated SVG placeholders in `app/img/[slug]`.

`AGENTS.md` is regenerated by `next dev` and warns this Next.js version differs from training data: check `node_modules/next/dist/docs/` before using Next APIs (e.g. `params`/`searchParams`/`cookies()`/`headers()` are async; `revalidateTag` takes a second argument).

## Commands

- `npm run db:local`: throwaway local Postgres (PGlite, :54330, data in `.pgdata`; stop it by killing the node process, delete `.pgdata` to reset). One connection only, so **concurrency tests can't pass on it**. Local `.env`: `DATABASE_URL=postgres://postgres:postgres@127.0.0.1:54330/postgres`, `PAYMENT_PROVIDER=mock`.
- `npm run dev`: dev server on :3000. Needs `.env` (copy `.env.example`).
- `npx drizzle-kit generate --name <x>` then **review the SQL**, then `npx drizzle-kit migrate`. Don't use `drizzle-kit push --force` (applies blindly; the harness blocks it). `npm run db:push` exists but prompts.
- `npm run db:seed`: idempotent seed (products, promos, admin). Prints the admin password once, only when it creates the admin.
- `ADMIN_EMAIL=… npx tsx scripts/reset-admin-password.ts`: sets a new random admin password (prints it once, signs out the admin's sessions). Uses the DB in `.env`.
- `npm run typecheck`, `npm run lint`, `npm run build`.
- `npm run test:integration` needs a **real Postgres** in git-ignored `.env.test` (`npm run db:migrate:test` first on a new DB). It currently holds a copy of the sibling project's disposable Neon test DB (same schema; tests tag and delete their own rows). Plain `npm test` uses the `.env` DB, and its concurrency tests fail on PGlite.
- `npm test`: Vitest, unit **and integration**, against the `.env` DB (see Gotchas). Unit only: `npx vitest run tests/unit`. Single file: `npx vitest run tests/integration/commerce.test.ts`; single test: `-t "oversell"`.
- `npm run build && npm run test:e2e`: Playwright against the **production build** on :3100 (it starts its own server; stop anything else on 3100). Headless unless `HEADED=1`. `npx playwright test -g "<title>"` for one test. It uses `.env`'s DB (local PGlite is fine) and, with `PAYMENT_PROVIDER=mock`, the checkout test stops after asserting the server-computed amount instead of opening the Razorpay modal. Restart the PGlite process if tests start failing with `ECONNRESET`.
- `npx tsx scripts/release-test-orders.ts`: cancels pending orders the e2e suite leaves behind (they hold reserved stock).
- CI (`.github/workflows/ci.yml`): typecheck, lint, unit tests, build, `npm audit`; no integration tests (they need a real DB).

## Architecture

**Money and stock core** (the part that needs several files to understand):
- All money is integer paise. Prices/totals are computed server-side in `lib/pricing.ts` (`computeTotals`, pure) from DB prices; the client only sends variant ids + quantities. `/api/checkout` builds lines from the **server cart** and ignores any price fields in the body.
- `lib/checkout.ts` `startCheckout`: one transaction does price lookup, promo claim (atomic `UPDATE ... redeemed < max`), `reserveStock` (guarded `UPDATE variants SET reserved = reserved + n WHERE on_hand - reserved >= n`, locked in id order), order + lines + reservations (30 min). The provider order is created *after* commit; on failure the order is cancelled. Idempotency key is unique on `orders`; the race loser polls for the winner's order. `order_lines` snapshot name/price, so later price edits never change existing orders.
- `markOrderPaid` (same file) is the **only** place an order becomes paid. Both `/api/razorpay/verify` (browser handler signature, then fetches the payment from Razorpay for amount/status) and `/api/razorpay/webhook` (HMAC over the raw body, deduped via `payment_events` inside the same transaction) call it. It row-locks the order, checks amount/currency (mismatch -> `needs_review`), commits reservations (`on_hand -= qty, reserved -= qty`), and handles late payment on an expired/cancelled order by re-taking stock if still available.
- `lib/inventory.ts`: `cancelPendingOrder` and `releaseExpiredReservations` (lazy at checkout start, plus `/api/cron/release` with `CRON_SECRET`, called every ~10 min by `.github/workflows/cron.yml`). DB `CHECK` constraints back all of this (`reserved <= on_hand`, no negatives).
- `lib/orders.ts` is the status state machine; admin status changes go through `app/actions/admin.ts` and write `order_events`.
- `lib/payments/` is a `PaymentProvider` interface with `razorpay` and `mock` implementations; `PAYMENT_PROVIDER=mock` enables `/api/mock/pay` (404 otherwise). `lib/env.ts` rejects `rzp_live_` keys.

**Admin** (`/admin`, role `admin`): stock, price/compare-at per size, size name + dimensions (`setVariantSize`), product details, add a size, archive, order status, promos (create, activate/deactivate via `endsAt`). Server actions in `app/actions/admin.ts` do `requireAdmin` + zod + revalidate and delegate DB logic to `lib/admin-catalog.ts` (so it is integration-testable without a session: `tests/integration/admin-catalog.test.ts`). Prices are per **variant** (`variants.priceCents`); listings show the cheapest size's price with *that* size's compare-at (`lib/catalog.ts`, product page).

**Cart and auth:**
- Anonymous cart = DB rows keyed by an HMAC-signed `cart` cookie; signed-in cart = by `userId`. `AuthForm` calls `mergeCartAfterSignIn` and `router.refresh()` **before** navigating, so protected pages see the new session.
- Roles: `user.role` (`customer`|`admin`). Authorization is enforced inside every server action/route (`requireUser`/`requireAdmin` in `lib/auth.ts`); `app/admin/layout.tsx` 404s non-admins.
- The Navbar reads cookies (cart count), so every page is dynamic; `revalidate` exports are inert.

**Data:** `db/schema.ts` is the source of truth (Better Auth tables included, plus `role`); migrations are in `drizzle/`. `lib/db.ts` uses one shared `pg` Pool (SSL on unless localhost, statement/connection timeouts, idle-error handler). `lib/catalog.ts` does listing/search with raw SQL (Postgres FTS + `ILIKE`).

**Ops stack** (all env-driven, each degrades gracefully when unset in dev):
- `lib/logger.ts` (`log.info/warn/error`): JSON to stdout, batched to Axiom (`AXIOM_TOKEN`/`AXIOM_DATASET`), and `log.error` also goes to Sentry. Prefer it over `console.*` in server code.
- Sentry: `instrumentation.ts` (server, `onRequestError`), `instrumentation-client.ts` (browser), `app/error.tsx` + `app/global-error.tsx` report. Source-map upload only when `SENTRY_AUTH_TOKEN`/`SENTRY_ORG`/`SENTRY_PROJECT` are set; `next.config.mjs` loads `withSentryConfig` via `createRequire` + a direct `build/cjs/config/index.js` path because the package entry Node resolves doesn't export it (may break on a Sentry upgrade).
- `lib/rate-limit.ts` (async, `await` it): Redis (`REDIS_URL`, atomic INCR+PEXPIRE) with in-memory fallback on no URL or Redis errors. `lib/client-ip.ts` takes the first `X-Forwarded-For` hop.
- `lib/email.ts` `sendReceipt`: Resend when `EMAIL_TRANSPORT=resend` (needs `RESEND_API_KEY`, `EMAIL_FROM`), else console. Never throws. Without a verified domain, `onboarding@resend.dev` only delivers to the Resend account owner.
- `lib/env.ts`: in a non-localhost production runtime it fails fast without `CRON_SECRET` (16+), webhook secret, Redis, Resend, Axiom, Sentry, https `APP_URL`, and forbids `PAYMENT_PROVIDER=mock`. Localhost prod builds (e2e) are exempt.
- `/api/health` (DB `select 1`) is the uptime probe. CSP/HSTS are set in `next.config.mjs` (CSP allows Razorpay and Sentry ingest hosts; add new third-party hosts there).

**Deployment:** not deployed yet. Options: Vercel (env vars in the dashboard, `NEXT_PUBLIC_*` inlined at build time) or the `Dockerfile` (standalone output) + `deploy/` (compose + Caddy) + `DEPLOY.md` free Oracle VM. It needs its own new Neon DB, Redis, Resend, Axiom and Sentry; never point it at the clothing store's DB.

## Gotchas

- `lib/*` files import `server-only`; Vitest aliases it to `tests/stubs/empty.ts`. `vitest.config.ts` forces `PAYMENT_PROVIDER=mock` and `EMAIL_TRANSPORT=console`, so tests never call Razorpay or send mail.
- `.env` currently points at the throwaway local PGlite DB. Once it points at a hosted/production DB, `npm test`, `db:seed`, `release-test-orders` and e2e write to it: confirm first and prefer `npm run test:integration`.
- `env()` caches its first result; tests that change env vars need `vi.resetModules()`.
- Drizzle wraps driver errors: the Postgres code is on `error.cause.code`. Checkout only returns messages of errors without a `cause` to clients (driver errors may contain SQL).
- Don't add a root `loading.tsx` (streams before `notFound()`, producing HTTP 200 soft-404s). The skeleton lives in `app/products/(list)/loading.tsx`.
- Card headings must keep the outline sequential: `ProductCard` takes `level={2}` under a page `h1`.
- The Razorpay webhook rejects everything until `RAZORPAY_WEBHOOK_SECRET` is set (needs a public URL; configure it in the Razorpay test dashboard).
- `.env`, `.env.test` and `.env.production` are git-ignored; keep secrets out of `.env.example`, README and commits.
- The Read/Write tools may be limited to one working directory; when working across the sibling projects use Bash, or ask for `/add-dir`.
- Windows checkout: files have mixed CRLF/LF, so multi-line string replacement scripts can silently miss (use the Edit tool and re-run typecheck). Big `bash` heredocs with backticks/quotes can fail to parse; write the file with the Write tool instead.
